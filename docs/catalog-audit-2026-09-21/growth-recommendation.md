# Повторна перевірка індексації та пріоритети зростання

Перевірено 21.09.2026: поточну production-базу в read-only транзакції, фактичний HTML вибірки сторінок, sitemap і серверний код. Політику індексації під час цієї перевірки не змінювали. Показані в Search Console 19,4 тис. проіндексованих URL станом на 18.09 — окремий показник від поточних robots/sitemap. Наявного скриншота недостатньо для встановлення причини 300 показів на тиждень або штрафу Google.

## 1. Перший пріоритет: помилково закриті сторінки каталогу

Підтверджено HTTP 200 + `noindex, follow` на:

- `/catalog/advokaty/kyiv`
- `/catalog/advokaty`
- `/catalog/stomatologiyi/kyiv`
- `/catalog/restorani/lviv`

Ці сторінки передаються в sitemap. Батьківська `/catalog/catalog-yurydychni-poslugy/kyiv` та перевірена сторінка послуги `/catalog/stomatologiyi/kyiv/implantaciia-zubiv` віддають `index`.

Причина підтверджена в production `CatalogPageController`: `landing()` підставляє `sub` для категорій із батьківською категорією; потім `index()` через `$request->filled('sub')` вважає цей внутрішній параметр додатковим фільтром і вимикає індексацію. Це окрема помилка від навмисного суворого режиму профілів.

У поточному sitemap 2 319 посадкових URL: 606 категорійних та 1 713 сторінок послуг. За ієрархією категорій попереднього знімка **419 категорійних URL потенційно підпадають під цю помилку**. Це розрахунок масштабу, не результат HTTP-перевірки всіх 419 сторінок. Докази: `growth-live-pages.json`, `growth-landing-check.json`, список `growth-affected-landings.json`.

Потрібне виправлення: відрізняти категорію, визначену URL, від додаткових користувацьких фільтрів. Зберегти noindex для пошуку, сортування, додаткових фільтрів, пагінації й недостатньо заповнених посадкових. Перевірити дочірню категорію з містом і без міста, батьківську категорію, справжній `?sub=`, інші фільтри та відповідність sitemap/HTML.

## 2. Профілі: вибіркове відкриття замість глобального перемикача

На час перевірки: 34 228 публічних профілів, 3 708 проходять поточний strict-фільтр, 30 520 отримують noindex.

Серед закритих (групи перетинаються):

| Ознака | Профілів |
|---|---:|
| Лічильник відгуків ≥1 | 14 538 |
| Лічильник відгуків ≥10 | 7 979 |
| Опис без HTML ≥120 символів | 8 653 |
| Є прив'язані послуги | 11 397 |
| Є місто, адреса та телефон або сайт | 29 196 |
| Немає відгуків, опис коротший за 120 символів і немає прив'язаних послуг | 10 827 |

Ці ознаки самі по собі не доводять актуальності, оригінальності чи якості даних. Кількість відгуків узято зі збереженого лічильника профілю.

Знайдено 3 088 попередніх кандидатів, у яких одночасно ≥10 відгуків, опис ≥120 символів, місто, адреса, контакт і рівно одне джерело. Після виключення ВСІХ профілів, позначених попереднім аудитом, залишається **2 902 кандидати для перевірки**, а не 2 902 готові до автоматичного відкриття сторінки. Список: `growth-candidates.json`.

Приклади фактичного HTTP 200 + noindex:

- «Дім Мулярових»: 100 відгуків, опис 468 символів.
- «Copper Head»: 100 відгуків, опис 478 символів.
- «Urban Space 100»: 100 відгуків, опис 293 символи.

Поточний фільтр не враховує насиченість цих сторінок імпортованими відгуками або послугами: їм бракує іншого сигналу чи 500 символів. Це підстава перевірити їхню корисність, а не автоматично визнати їх унікальними.

Почати з 100–300 вручну перевірених кандидатів у тих самих категоріях/містах, де розвиваються посадкові. Це рекомендований розмір керованого експерименту, не вимога Google. Дозволяти index за відсутності змішаних джерел/дублікатів, правильності категорії й географії, достатності підтверджених фактів для вибору користувача та наявності корисного змісту. Порожні та нерозібрані профілі залишити закритими. Саме подовження тексту до 500 символів чи генерація AI-досьє не є перевіркою якості.

Додаткова неточність поточного фільтра: native-review сигнал перевіряє відгуки без фільтра `status=published`; приватний pending/hidden відгук може впливати на доступність індексації. Критерій варто обмежити опублікованим змістом. Загалом знайдено 15 published, 3 hidden, 1 pending нативних відгуків; число профілів, які відкриті виключно через неопублікований відгук, тут не визначалося.

## 3. Як нарощувати корисний пошуковий трафік

1. Усунути підтверджений noindex-конфлікт на канонічних категорійних посадкових. Вибрати близько 20 пріоритетних сторінок категорій/послуг у 2–3 напрямах і кількох містах; остаточно визначити їх за запитами й показами Search Console, а не за припущенням про попит.
2. Покращити можливість вибору на цих сторінках: відповідність компаній потрібній послузі, актуальні факти, зрозуміла методика рейтингу, перевірені відгуки з джерелами, відповіді бізнесу. Пошук назви послуги в імпортованому відгуку сам по собі не доводить, що бізнес зараз її надає.
3. Забезпечити зрозумілі внутрішні посилання з відповідних профілів і категорій. Сторінки послуг уже існують; не потрібно генерувати ще тисячі подібних URL без попиту й даних.
4. Розвивати власний контент Dovira через добровільне підтвердження профілів бізнесами, уточнення послуг і збір справжніх відгуків їхніх клієнтів. Віджети/посилання бізнесів мають бути добровільними; без накручених відгуків або обов'язкових SEO-посилань. Це продуктова рекомендація, не виконана розсилка.
5. Окремо вимірювати фактичну індексацію, небрендові покази, кліки, релевантність запитів та звернення. Порівнювати вибрану групу з подібними сторінками без змін, зазначити дату виправлення; перші 4–6 тижнів — період спостереження, не обіцяний строк зростання. У Search Console перевірити однакові тип пошуку, країни, дати та фільтри.

Для точного вибору пріоритетних URL бракує експорту Search Console «Ефективність»: сторінки й запити за останні 3 місяці, та причин неіндексації. Скриншот загальної індексації не показує позицій і причин низької видимості. Підтвердження штрафу Google немає; коментарі в коді про «демоцію» не є доказом.

Джерела Google: [корисний контент](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [діагностика падіння трафіку](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops), [sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview).

Рекомендований порядок: виправлення канонічних посадкових → перевірена тестова група профілів → розвиток корисних даних та повторне вимірювання. Глобальне вимкнення strict-режиму зараз не рекомендовано.
